# 故障复盘与恢复验收

将已查证事实组织成可供业务、研发与运维共同评审的复盘。默认中文，先给结论与当前状态；正文简洁专业，图表解释关键机制，原始日志、SQL、提交与验证明细放附录。按事件规模选取必要内容，不为凑章节扩大调查或填造结论。

## 适用与取证

- 编写新复盘：读取当前任务已有代码、日志、发布记录、测试和历史材料，优先复用已取得的证据。缺少关键事实时做范围内只读核验，或明确写出待确认项与所需证据。
- 更新复盘：先读取目标最新版本，保留用户改动；只更新请求涉及的事实与其关联摘要、时间线、图表、验收结论，避免正文互相矛盾。文案修改无需重跑生产验证。
- 验收恢复：只有用户要求验收或任务已有授权时，查询当前发布、实例、数据库变更状态及必要业务结果。执行查询类业务请求前核对目标环境、参数契约及副作用。
- 复盘不授权部署、DDL、重试写入、回滚、发送消息或扩大分享。建议措施与已实施措施分开。

## 核心内容

按阅读需要组合以下要素；只有相关时才展开。需要完整报告或时间口径时，读 [结构与证据口径](references/report-elements.md)。

1. **一句话结论与现场**：受影响业务、症状、故障发生环节、代表性请求与错误；当前修复、发布、恢复验收和剩余工作分别标状态及核验时间。
2. **时间线与人员**：变更开发 / 合入 / 发布、首次已知失败、发现、处置、修复发布、成功验收。引入人与发布人分别依据 commit / MR / 发布工单归属，自动合并账户不冒充实际作者。
3. **影响范围**：已证实的用户、请求、功能和时间范围；潜在同类风险另列。检索无结果不等于无影响，单个样本不能推断全量。
4. **根因与触发条件**：业务调用链 → 具体故障点 → 底层机制 → 错误传播。说明变更目的、为何引入问题、在什么输入或规模下触发；区分根因、放大因素和重试影响。
5. **前后对比**：旧 / 新执行过程、改动范围、业务不变量、测量结果及副作用。数据口径一致才比较，不用失败调用总耗时计算 SQL 优化比例。
6. **漏检与预防**：实际已有测试覆盖什么、漏掉什么、哪些历史记录缺失；提出能在测试或发布前捕获同类问题的具体样本与检查，而非“加强测试”。
7. **交付与验收**：代码 / 制品 / 发布 / 数据变更 / 业务结果各自有证据。记录实际参数、环境、时间、结果、范围和限制；未执行事项保留待验收，建议不标已落地。

## 不可混淆的证据边界

- **引入日期 ≠ 首次故障日期；风险暴露窗口 ≠ 连续故障时长。** 条件组合分阶段上线时，分别记录底层问题引入和业务路径暴露。
- **发布完成 ≠ 实际首次恢复。** 成功验收证明“最迟此时该场景已恢复”；没有连续观测或历史成功记录时，实际首次恢复与连续故障时长仍未知，不能将已知验收时间也笼统写成“恢复时间未知”。
- **现场日志 ≠ 同条件复现。** 图、标题和正文均注明证据来源。例如日志仅证明召回断连，而末页超时由 SQL 复现确认，就不能写成现场已定位具体失败页。
- **提交 ≠ 发布；工单批准 ≠ 执行；执行中 ≠ 生效；生效 ≠ 性能收益确认。** 状态字段相互矛盾时结合阶段、子任务进度、实际元数据与业务结果判断；无法判定则保留冲突，不把零时间戳解释为未开始。
- **预计扫描行数 ≠ 实测扫描行数；结果数 ≠ 扫描数；复用既有测试结果 ≠ 本轮重新测试。** 示例数字明确标为示意。

## 图文与 HTML

用户指定格式优先。需要图文 HTML 时，读 [HTML 呈现与交付](references/html-delivery.md)。简单事件可用短文加一张表；不自动将所有复盘做成长网页。

更新机制说明时，以实际执行证据为准，不能仅从 SQL / 代码语法推断物理顺序。用一张调用链定位故障，再用前后并排图或表解释执行差异；不要混成一张巨图。用户要求解释术语时在相应位置简短补充，不扩写通用教程。

## 交付检查

核对摘要与正文状态一致；时间及持续时长可追溯；人物角色有出处；图中确定性不高于证据；前后指标口径一致；未完成事项与观察截止时间明确。交付说明实际更新、验证结果和必要限制，不把文档上传成功称为生产验收成功。
