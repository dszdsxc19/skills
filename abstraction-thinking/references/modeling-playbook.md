# Modeling Playbook — 形式化工具箱

目标：找到**足够小但足够真实**的模型，避免“看似优雅却遗漏核心语义”。

## 选择哪种形式？

| 问题结构 | 适合的表达 | 何时不要直接使用 |
| --- | --- | --- |
| 能力对输入生成输出 | `F: X → Y` | 运行结果依赖隐式状态、副作用、权限、时间而未声明 |
| 同类输入上的独立批量操作 | `Batch(D,F)=Map(F,D)` | 输入存在跨行依赖、全局约束、原生批量语义不同 |
| 固定流水线 | `F = fₙ ∘ … ∘ f₁` | 分支、循环、动态规划、人类审批是关键特征 |
| 任务生命周期 | `δ: S × E → S` | 需要考虑并行、竞争状态时，单状态机可能不充分 |
| 有效状态约束 | `∀s∈Reachable, I(s)` | 无法定义可观察状态和明确的断言 |
| 多目标方案选择 | `min Cost(x)` s.t. `Constraints(x)` | 成本指标或限制条件只是主观猜测 |

## 六个严谨性问题

1. **对象域**：符号代表数据、业务能力、任务还是一次调用？是否有唯一标识和版本？
2. **次序**：数据集 `D` 是无序集合还是有序序列？如果结果要对齐原输入，优先采用序列或显式 `input_id`。
3. **结果**：返回纯 `Y`，还是 `Result<Y,Error>`、`Execution`、事件流？
4. **依赖**：`F(d_i)` 是否独立？会调用外部资源、修改数据库或受全局配额影响吗？
5. **时间**：返回的是完成结果，还是“已接受执行”的确认？哪些状态最终一致？
6. **反例**：是否能给出一个满足当前自然语言表述但违背公式假设的场景？

## 从简单模型递进到工程模型

### 纯映射（适合解释概念）

设 `F: X → Y`，`D=(x₁,…,xₙ)`，且各次调用相互独立：

`Batch(D,F)=(F(x₁),…,F(xₙ))`

这个模型推导出“批量引擎只需知道如何对一个输入调用 F”，但**不**推导出“具备可靠调度、取消和重试”。

### 含运行状态（适合异构执行引擎）

`Run(F,x,policy) → execution_id`

`Observe(execution_id) → {state, progress?, result?, error?}`

`δ(state,event) → state'`

由此推导：将执行实例与能力定义分离；Batch 只持有一组 execution_id；各运行时 Adapter 负责将自身状态投影到通用状态模型。

如果没有稳定任务 ID、幂等键或查询接口，应明确当前适配层无法保证任务恢复，不能宣称已经完全统一。

### 组合与动态 Agent

`Workflow = fₙ ∘ … ∘ f₁` 适用于静态线性工作流。

如果 Agent 会自主决定下一步，则更恰当的模型是：

`aₜ = π(contextₜ)`

`contextₜ₊₁ = Step(contextₜ, aₜ)`

这两者可以共享外部执行契约，但不能因为都“执行一些步骤”就认定内部语义相同。

## 从公式推导技术边界

- **F 是可替换对象** → 抽取 Capability Contract 与版本，业务能力不依赖使用方。
- **底层运行实现可变** → Adapter 按协议/引擎复用，而不是按每项业务重复编写。
- **运行过程拥有状态** → 引入 Execution Manager；批量任务与单次任务解耦。
- **存在数据驱动重复调用** → Batch Engine 只依赖 `Run` 和 `Observe`，而非后端类型。
- **副作用与失败不可忽略** → 幂等键、结果对齐、审批、重试策略属于显式契约。

## 快速质量检查

优秀输出必须回答：

- 这个模型比原问题少了哪些偶然细节？
- 它真正新增了什么可执行或可验证的洞察？
- 它在哪种具体情况下会失效？
- 如果去掉数学符号，是否依然是清晰且正确的解释？

任一回答不清楚，就简化模型、补上假设，或不使用形式化表达。
