# 示例：从复杂场景到最小模型

这些是行为示范，不是要求每次原样输出。推导应围绕用户实际关心的决策。

## 示例 A：统一 API / Canvas / Agent 的批量执行

**问题**：我们希望一个批量工作台同时调用 API、画布和 Agent；每个业务场景都写一套批量流程很浪费。

**本质**：批量是对一组输入重复应用某项可执行能力；“后端类型”不是批量逻辑的一部分。

**概念模型**：

`Batch(D,F)=Map(F,D)`

- `D`：有序输入数据集，包含输入记录的稳定 ID。
- `F`：符合统一调用契约的业务能力，而不是某个特定 API。
- `Map`：对每条输入执行能力，并保留输入与结果的关联。

**推导**：

1. 批量层应依赖 `F` 的描述与运行契约，而非 HTTP/MCP/Agent 的实现细节。
2. Adapter 应按 HTTP、画布运行引擎、Agent 运行引擎复用；同种运行引擎的新增业务优先只配置。
3. 能力注册后，批量、评测、定时运行等上层操作都能重用同一个执行入口。

**边界**：该模型假设逐项执行可分解。当运行耗时很长或会产生副作用时，需要 `Run(F,d) → execution_id` 和执行状态机；分批策略、重试与成本不能从 `Map` 自动得出。

## 示例 B：为什么 Workflow 与 Agent 看起来类似？

**问题**：Agent 和 Workflow 都会执行多步任务，是不是同一种东西？

**本质**：两者都可以对外暴露 `Run(input) → execution`，但是“下一步由谁决定”不同。

**模型**：

- 静态流程：`F = fₙ ∘ … ∘ f₁`（简化为线性路径）。
- 动态 Agent：`actionₜ=π(contextₜ)`，`contextₜ₊₁=Step(contextₜ,actionₜ)`。

**推导**：统一运行管理、身份、审计与结果交付是有理由的；统一内部编排算法则没有必然性。可以让两种引擎共享 Execution Contract，但保留不同 Runtime。

**边界**：Workflow 也可能有条件、循环和动态分支；Agent 也可能受固定步骤约束。区分标准是规划机制及约束，而不是名字。

## 示例 C：批量任务和单次执行该如何拆分？

**问题**：一个视频任务可能运行几分钟，批量 100 个视频时怎么统一进度和恢复？

**模型**：

`Batch = (D, {e₁,…,eₙ})`

`Run(F,dᵢ) → eᵢ`

`δ(eᵢ.state,event) → eᵢ.state'`

**推导**：批量关注任务集合及汇总进度，执行层关注单个任务生命周期，Adapter 翻译后端任务状态；两者可以独立演进。

**边界**：取消可能只是请求取消，超时不意味着上游停止；重复提交可能重复计费，因此必须约束重试幂等。

## 示例 D：抽象服务的告警治理

**问题**：API、队列、数据库、视频任务的监控指标不同，是否能复用同一告警框架？

**候选模型**：

`Alert = Evaluate(metric_window, policy)`

**推导**：统一的是采样窗口、策略评估、通知及事件生命周期，而不是强迫所有业务指标相同。业务线通过指标与策略配置扩展框架。

**边界**：队列积压与请求错误率具有不同时间动态；一条静态阈值不足以描述所有故障，需支持窗口、持续时间和复合条件。

## 反例：不要强行公式化

**问题**：“我的 Mac 出现 unknown terminal xterm-ghostty，要怎么修？”

**不佳回答**：先写 `Terminal = Shell × Environment` 并抽象环境协商。

**更好的回答**：直接说明 TERM 与 terminfo 不匹配、提供检查与修复步骤。除非用户继续询问终端能力协商的通用设计原理，否则不启动本 Skill。
