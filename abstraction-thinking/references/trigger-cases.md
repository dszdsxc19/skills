# 触发测试样例（Trigger Cases）

用于检查 Skill 描述是否能够把“值得抽象的问题”与普通任务区分开。匹配是建议，不保证所有宿主平台都会自动触发。

## 应当考虑触发

| 用户请求 | 原因 |
| --- | --- |
| “同一个批量平台如何同时跑 API、画布和 Agent？” | 异构实现中的不变量与统一契约 |
| “这个架构能不能抽象成一个最简单的数学函数？” | 明确请求形式化 |
| “为什么不同产品最后都长出了 Workflow？” | 比较跨产品共性与形成机制 |
| “从第一性原理分析一下 Agent 的执行平台” | 明确请求第一性原理建模 |
| “我不想业务方都写 Adapter，该怎样反转依赖？” | 需要设计可复用的抽象边界 |
| “服务治理、告警和任务调度能共享什么底层思想？” | 抽象迁移 |
| “用一个概念模型解释静态工作流和动态 Agent 的关系” | 形式化与比较适用边界 |
| “这三个方案看上去不一样，究竟不变的核心是什么？” | 寻找不变量 |

## 通常不触发

| 用户请求 | 原因 |
| --- | --- |
| “ContextForge 的最新版本是多少？” | 事实核验 |
| “把这一段话润色得专业一点” | 文本改写 |
| “帮我修一下这个具体的 TypeScript 类型错误” | 明确的工程修复；先修问题 |
| “请计算 120×15 的结果” | 算术计算不是抽象建模 |
| “什么是 MCP？” | 普通概念解释，除非用户追问本质或跨协议抽象 |
| “给我推荐一本书” | 普通推荐 |
| “查看这个项目的 README 并列出安装步骤” | 信息整理与操作流程 |
| “把照片裁剪成 16:9” | 具体操作，无需本 Skill |

## 模棱两可的情形

- “这三个 API 为什么设计得不同？”：如果只是列差异，不一定需要；如果要设计一个通用 SDK，则应该触发。
- “Agent 到底是什么？”：普通定义不需要；若在多个 Agent/Workflow/Tool 架构之间求共同模型，则可以触发。
- “能不能写个公式？”：先判断模型是否带来解释力；无法精确形式化时可以坦诚说明，而不是硬造公式。
