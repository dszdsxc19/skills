# Abstraction Thinking / First-Principles Modeling

把复杂、具体的现象提炼为**最小而准确的本质模型**，再由模型推导可迁移的规律、设计决策及其成立边界。

本 Skill 的价值不是“给答案加一个公式”，而是**用抽象发现原本不明显的结构与机会**。优先保证问题被正确理解；模型服务于洞察，不服务于形式感。

## 什么时候使用

满足以下任一情况，且抽象预计能带来新的理解或决策价值时，主动使用：

1. **跨场景求共性**：用户把 API、Agent、画布、CLI，或其他不同系统放在一起讨论，想知道能否统一。
2. **设计抽象边界**：讨论平台化、通用组件、接口契约、插件架构、领域模型、执行框架、职责拆分。
3. **追问本质/第一性原理**：例如“本质是什么”“为什么这些东西长得这么像”“有没有更底层的解释”“能否用一个函数概括”。
4. **化繁为简**：讨论中出现许多实现细节，用户需要更短、更有解释力的概念模型。
5. **将洞察迁移到新问题**：一个领域里的结构是否能指导另一领域的产品或架构设计。
6. **为方案做判断**：多个技术方案纠缠不清，先需要找准不变量、可变点和约束，才能提出设计取舍。

**隐式触发**：即使用户没有明确要求公式，只要正在探讨跨场景的统一设计、复用机制、系统本质或架构演进，也可以自然地加入一个“核心抽象”。

### 什么时候不要使用

- 简单事实查询、术语解释、常规翻译、润色、日常对话，不需要额外建模。
- 用户只要一个直接操作步骤、具体修复或已有规范下的执行结果，形式化不能改善决策。
- 单纯数学计算不等于抽象建模；不要因为出现公式就触发。
- 需要真实数据、代码证据、现行文档或实测才能下结论时，先核实事实；模型不能替代证据。
- 无法提取真实的不变量，或公式仅仅是对自然语言的换皮时，宁可不用公式。

## 工作流程（CIFDV）

### 1. Concrete：抓住具体问题

先用一句话说明：**用户真正想解决的是什么？**

识别：典型场景、输入、输出、核心操作、约束、失败模式、用户实际关心的决策。不要把眼前的 API 名称、UI 形态、框架类型误判为问题本质。

### 2. Invariant：找不变量和变化维度

对不同案例提问：

- 哪一部分无论底层实现怎么换都保持不变？
- 哪一部分只是一种实现方式、协议或部署形式？
- 哪些行为事实上不等价，不能硬放在一起？

明确区分**公共契约**、**可替换实现**、**执行策略**、**环境约束**。必要时寻找一个能推翻候选模型的反例。

### 3. Formalize：用尽量小的模型表示

优先选择最贴切的形式，而非最复杂的数学：

- 函数 `F: X → Y`：描述可调用能力与输入输出契约。
- 映射 `Map(F, D)`：描述同一能力应用于多项输入。
- 函数组合 `fₙ ∘ … ∘ f₁`：描述确定的顺序处理链。
- 状态转移 `δ: S × E → S`：描述异步任务、事件和生命周期。
- 谓词/不变量 `I(s)`：描述必须始终满足的条件。
- 约束优化：描述成本、延迟、质量之间的取舍。

**默认只给 1 个核心公式或结构模型。** 每个符号都要解释现实含义；写清输入输出、假设和适用范围。模型不需要数学化时，用一句精确的规则、状态图或关系图即可。

### 4. Derive：由模型推导新结论

这是 Skill 的核心步骤。至少提出 1 条**不是简单复述问题**的结论，理想情况下 2～3 条：

- 哪些模块能够解耦？
- 哪些能力可以跨场景复用？
- 接口边界、数据契约或执行管理应该如何设计？
- 新的产品交互方式、验证方法或演进路径是什么？

明确说出推导逻辑，例如：`因为 Batch 只依赖 F 的契约，所以 Batch Engine 不必依赖 HTTP/Agent/Canvas 的具体实现。`

**抽象迁移**：有价值时指出相同模型还可用于哪些其他领域，但不要因外表相似就断言机制等价。

### 5. Validate：检查边界和反例

主动验证：

- 模型成立依赖什么前提？
- 如果有异步执行、上下文状态、顺序依赖、副作用、部分失败、重试或人工介入，会怎样？
- 概念模型是否被错误当成完整实现方案？
- 需要补充哪些数据或实验才能验证设计？

必要时把简单模型升级为执行模型，例如 `Run(F, x) → Execution`，而不是强行坚持 `F(x) → y`。

## 回答方式

自然嵌入用户原本的对话，不要求固定模板。复杂讨论可按以下顺序：

1. **一句话本质**：先给直觉化总结。
2. **核心抽象**：展示 1 个极简模型，解释符号。
3. **推导出的结论**：2～3 个可用的洞察或架构决策。
4. **成立边界**：用简短反例避免过度泛化。
5. **下一步**：只有在用户需要方案时，给出设计/验证建议。

轻量对话只需“一句话 + 一个模型 + 一条推论”，不必机械地列出五步。

语言优先跟随用户。用户用中文时，以中文解释，必要时保留准确英文技术词。不要为了显得深刻而堆砌抽象术语、箭头图或 LaTeX。

## 正确性约束

- **第一性原理 ≠ 任意类比。** 尽量从可观察事实、必要条件与显式假设推出结论；类比只是启发，不是证明。
- **概念抽象 ≠ 运行时保障。** `Map(F, D)` 不天然保证幂等、并发安全、重试语义、顺序一致、成本可控。
- **协议 ≠ 执行模式。** HTTP/MCP 描述调用途径，同步/异步/流式描述执行与交付；不要混为一个枚举。
- **数据形式 ≠ 计算语义。** Workflow 画布是设计界面，不必然定义特定执行协议。
- 明确标注“这是便于理解的模型”还是“这是可实施的接口/状态机”。
- 不要凭公式声称某产品已有某功能；需要时核实产品资料与代码。
- 不主动生成代码，除非用户明确要求实现。
