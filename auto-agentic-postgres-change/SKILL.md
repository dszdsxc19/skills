# Auto-Agentic PostgreSQL Change

把共享 PostgreSQL 变更做成可证明目标、可限制风险、可重复执行、可验证结果的闭环。这里的核心风险不是 SQL 能否运行，而是把正确的变更执行到了错误的配置域或错误的数据库。

## 授权边界

先从用户动词判断本轮权限，不能把相邻动作合并解释：

- “看看、分析、设计迁移”只允许只读检查和方案输出。
- “实现迁移”允许修改迁移代码和测试，不代表允许连接或修改任何共享数据库。
- “执行迁移、修改数据库”只有在目标数据库及访问配置链明确后，才允许通过下述门禁执行对应变更。
- 删除表/列、覆盖数据、大范围回填、收紧约束等难恢复动作，即使用户已同意一般迁移，也需要把精确影响和恢复方案说清楚后获得针对该动作的明确授权。
- 提交、推送、部署和数据库执行彼此独立；用户授权其中一项不自动授权其他项。

没有目标数据库写权限时仍可完成代码、测试和只读预检，但必须停在实际执行之前。

## 动态解析执行上下文

每次都从当前代码、平台和用户授权动态解析这些事实，不要把任何泳道、标准环境、PSM、部署类型或本地执行身份固化在 Skill 中：

- 应用目录：`apps/auto-agentic-app`。
- 服务 PSM、部署类型和标准环境：从当前部署配置或平台回读。
- 目标部署泳道：来自用户本轮明确指定；未指定且无法从任务上下文唯一确定时停止询问。
- 本地执行身份和运行 wrapper：从当前项目脚本、已验证命令或用户提供的执行上下文解析。
- 数据库连接必须由应用的 `getAppConfig()` 读取 TCC `DATABASE_URL`，不得复制连接串、从日志回显连接串或把真实连接串写入仓库。

部署泳道、TCC 配置上下文和 PostgreSQL 实例是三个不同层次：它们可能一一对应，也可能多个环境共享同一个数据库。平台回读只证明服务部署归属，不能单独证明数据库身份；数据库身份必须由实际连接的非敏感指纹、库名、Schema、主从状态和用户确认共同证明。

## 工作流

### 1. 建立代码事实

1. 读取仓库根目录、应用目录及目标目录最近的 `AGENTS.md`。
2. 运行 `git status --short --branch`，保留用户已有 WIP，只允许修改本次迁移相关文件。
3. 找到数据库配置入口、现有 Schema 方法、仓储调用和发布期脚本。先判断需求是新增结构、兼容演进、数据修复，还是删除/替换。
4. 列出成功条件：目标表、列、索引、约束、预期数据变化和历史业务不变量。

### 2. 设计最小安全迁移

优先使用可安全重跑的增量 DDL：

- 新表使用 `CREATE TABLE IF NOT EXISTS`，但仍要在后验检查中验证完整列和约束；“表已存在”不代表结构正确。
- 历史表新增字段优先可空；需要 `NOT NULL` 时采用“可空字段 → 分批回填 → 验证 → 收紧约束”的分阶段方案，或证明安全默认值不会改变历史语义。
- 新增唯一索引或唯一约束前先查重复键。发现重复时停止，不自动删除、合并或覆盖历史数据。
- 普通索引会阻塞写入时，评估表大小、写流量和锁窗口；大表或热点表优先设计 `CREATE INDEX CONCURRENTLY`，并注意它不能放在普通事务块中。
- 多实例可能同时执行的 Schema 准备使用事务级 advisory lock；不同迁移域使用不同 lock key。
- 为新迁移设置有界 `lock_timeout` 和 `statement_timeout`。超时的意义是让迁移安全失败，不能在捕获后无条件重试。
- 显式迁移入口只负责数据库结构，不初始化 Mastra、Agent、请求服务或后台 Worker。
- 不把 DDL 放进请求热路径或服务启动钩子；发布实例并发启动会放大锁竞争和部分失败。
- 迁移失败后应能从已完成步骤继续重跑，不依赖人工猜测“执行到哪一步”。

优先采用 expand/contract 顺序：先发布向后兼容的新增结构，再发布同时兼容旧/新结构的代码，随后分批回填和验证，最后在独立变更中收紧约束或清理旧结构。

数据变更必须额外说明筛选条件、预计影响行数、分批策略、审计字段和恢复来源。先用同一 `WHERE` 做只读计数和抽样；执行时使用确定性主键顺序、单批上限和可重复判断，禁止无 `WHERE` 的 `UPDATE`/`DELETE`。没有可靠恢复来源时，不执行破坏性数据变更。

### 3. 实现和本地验证

1. 把具体 Schema 方法组合到单一部署期迁移函数。
2. 提供显式 package script；连接池使用最小连接数，执行完成后关闭连接并明确退出。
3. 为迁移顺序、事务边界、advisory lock 和失败传播写定向测试。
4. 运行定向测试、相关回归、类型检查、Lint 和 `git diff --check`。按风险选择范围，不用无关全仓失败掩盖目标迁移结果。
5. 执行前记录 `git rev-parse HEAD` 和目标迁移差异。迁移代码未提交时，不能静默把 WIP 当正式版本；只有用户对当前 WIP 的共享数据库执行授权明确时才继续，并在结果中报告。

### 4. 唯一定位目标数据库与配置链

实际执行前必须读取 [目标数据库执行与验证](references/target-database-execution.md) 全文，并完成其中的上下文解析、非敏感指纹和 PostgreSQL 预检。

关键不变量：

- `doas` 的区域、部署泳道 HTTP Header 和 TCC 运行上下文都不能单独证明数据库身份。
- 不默认注入任何固定 `SERVICE_ENV`、`TCE_ENV` 或其他环境变量；只有当前目标确实要求模拟指定运行上下文且该方式已经验证时才使用。
- TCC 明确读取失败并回退到 `process.env` 或本地 `.env` 时停止。单独出现本地 `.env` 探测日志不等于 TCC 已失败，应结合明确失败日志和配置结果判断。
- 只输出 `DATABASE_URL` 的短哈希用于比较，绝不输出原值。
- 不同部署或配置环境可能指向同一个 PostgreSQL。相同指纹应如实报告，既不能据此声称是两个库，也不能假设它们永远共库。
- 如果用户明确确认本地默认配置与目标环境共享数据库，可以使用本地已验证配置链执行；仍须通过数据库身份、指纹和前后验检查锁定实际目标。
- 无法证明目标数据库身份时停止；不能以“命令能连通”代替目标证明。

### 5. 只读预检

在与正式执行完全相同的配置链中检查：

1. 数据库名、Schema、角色、版本、是否只读副本和脱敏后的服务端指纹。
2. 目标表存在性、关系大小和估算行数；只对确认较小的表执行精确 `COUNT(*)`。
3. 预期新增列、索引、约束的已有状态；如果已有，验证定义而不是直接跳过。
4. 新唯一键的重复分组数、新约束的违规行数。
5. 活跃事务、最长事务时长、目标关系上的已授予锁和等待锁。
6. 业务不变量基线，例如历史行数、状态分布、非空字段数量和关键聚合。

出现以下任一情况时在写入前停止：目标指纹不确定、连接到只读副本、存在等待锁、长事务可能阻塞 DDL、表规模或写流量超出当前锁方案、唯一键有重复、约束有违规数据、迁移定义与已有同名对象不一致。

### 6. 执行

1. 再次确认用户已授权这个目标数据库、配置链和这组变更。
2. 使用 [目标数据库执行与验证](references/target-database-execution.md) 中解析出的同一个运行 wrapper 执行项目内已验证的 package script，不手工复制多条 DDL 到终端。
3. 以进程退出码和迁移入口的明确完成消息判断结果。日志中的本地容器目录警告可能只是环境噪音，但不能因此忽略真正的 SQL、TCC 或连接错误。
4. 执行超时或锁失败时停止并重新查询锁；不要无条件重试共享数据库 DDL。

### 7. 后验验证

使用同一个运行 wrapper 重新执行只读检查，并至少证明：

- 目标表、列、索引全部存在，且定义符合预期。
- 没有 invalid/not-ready 索引，没有未验证约束。
- 唯一键重复分组和约束违规行为零。
- 历史行数和业务聚合符合预期；纯 Schema 迁移不应改变历史数据。
- 没有遗留等待锁。
- 若迁移声明幂等，可在风险可接受时重跑一次并再次验证；不要仅凭 `IF NOT EXISTS` 宣称幂等。

部分步骤失败时，先查已落结构和事务边界。修复原因后只重跑经过证明的幂等入口；不要通过 DROP 已成功对象来“回到起点”。

## 兼容与恢复原则

- 加列默认保持历史任务为 `NULL`，避免把旧数据误标成新链路数据。
- 带默认值的非空列必须证明旧行语义，例如计数器默认 `0`。
- 局部唯一索引只约束新链路显式写入的键，可避免历史空值受影响。
- 新代码回滚时通常先回滚应用版本，保留向后兼容的新增表/列；自动 DROP 可能破坏仍在运行的实例。
- 破坏性迁移必须预先准备快照、反向迁移或可验证的数据恢复来源，并把恢复耗时计入方案。

## 结果报告

最终先给结论，再提供足够审计证据：

```markdown
数据库变更：已完成 / 未执行 / 受阻

- 目标：<用户指定的部署上下文 / 实际配置链 / database / schema，连接串不展示>
- 授权：<用户授权的具体动作>
- 迁移：<脚本和代码版本或 WIP 说明>
- 预检：<表规模、重复键、活跃事务、等待锁>
- 结果：<新增/已有的表、列、索引、约束>
- 后验：<缺失、失效、违规、行数变化、锁>
- 历史影响：<不变量是否保持>
- 剩余风险：<未验证项或后续动作>
```

不要在报告、命令输出整理或提交内容中包含数据库密码、完整 `DATABASE_URL`、Token、Cookie 或证书路径。
