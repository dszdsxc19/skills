# 读者优先技术文档

目标不是把材料写全，而是让目标读者用最短路径获得正确理解、完成接入或作出决策。

## 先确定读者任务

写作前明确目标读者、文档用途、读者读完需要回答的 1–3 个问题，以及合理的阅读时间。上下文足够时直接推断；只有不同答案会显著改变文档结构时才向用户询问。

对于技术能力或接入文档，可将以下问题作为默认起点，再按实际场景替换：

- 怎么调用？
- 规则怎么生效？
- 结果何时可信？

这三个问题不是通用模板。架构评审、故障复盘或决策文档应围绕各自读者真正需要回答的问题组织。

## 设计主阅读路径

- 首屏给出结论、整体心智模型或关键判断，不用背景铺垫占据入口。
- 主文只保留直接帮助理解、接入或决策的内容。文件清单、完整字段、实现细节、证据链接等不适合主阅读路径、但仍有效或有维护价值的信息，必须放入附录或可追溯的资料索引，不能因精简正文而直接丢弃。
- 不沿用源材料的章节逐节缩写；围绕读者问题重新组织，并设置一个明确的“读到这里即可决策”终点。附录不属于主阅读路径。
- 用户给出阅读时间时，将它转成正文预算。3 分钟评审的主阅读路径通常不超过约 1,200 个中文字符或 2–3 个普通页面视口；超出时必须下沉次要细节，而不是只在长文前增加摘要。
- 流程、架构、状态变化和因果关系在图示能明显降低理解成本时使用聚焦图；精确映射和对比使用表格；其余用简洁段落。
- 图表必须承担信息表达职责，不为满足“有图”而画图，也不要让正文重复复述图表。
- 同一关键事实只在一个位置完整表达；摘要、正文和结尾不要换一种措辞重复一遍。
- 沿用用户指定的体裁、模板和承载工具；若目标是飞书文档，按 `lark-doc` 与 `lark-whiteboard` 的规则创建和检查文档。

## 先选信息结构，再选绘图工具

图表设计顺序必须是：`读者问题 → 信息关系 → 图表类型 → 布局 → 绘图工具`。禁止从 Mermaid、SVG 或现有模板能够快速生成什么反推应该画什么；流程图也不是技术文档的默认图表。

每张图先写出一个不进入正文的验收问题，例如“本次新增服务部署在哪里”“请求按什么顺序调用哪些系统”“任务收到什么事件后改变状态”。一张主图只回答一个核心问题；如果问题中同时出现组成、部署、时序、状态和决策，应拆图而不是继续增加节点和箭头。

按读者问题选择表达形式：

| 读者问题 | 首选表达 |
| --- | --- |
| 系统由什么组成，模块边界和复用关系是什么 | 分层架构图或容器图 |
| 服务实际部署在哪里，哪些单元独立发布或扩缩容 | 部署拓扑图 |
| 一次请求如何依次调用多个系统 | 时序图 |
| 多角色或多系统分别承担什么责任 | 泳道图 |
| 实体有哪些状态，什么事件触发迁移 | 状态机 |
| 满足不同条件时走哪条路径 | 决策流程图 |
| 确定性的生产过程有哪些连续阶段和产物 | Pipeline 图 |
| 长且线性的 Pipeline 在纵向布局中不可读 | 横向蛇形 Pipeline |
| 每个阶段调用谁并输出什么 | `Step → Executor → Artifact` 产物链 |
| 用户从提交到获得结果经历什么 | User Journey |
| 精确对比、职责清单、字段映射或能力盘点 | 表格，通常不画图 |

选型后再决定工具。Mermaid 能稳定表达且最终视口清晰时优先使用；需要精确控制蛇形布局、容器嵌套、视觉层级或节点位置时使用 SVG。不得接受“工具成功渲染但读者体验差”的降级结果。

## 撰写与删减

先完成最短的主阅读路径，再补必要证据。每加入一段内容，都判断它服务于哪个读者问题；无法对应且不影响正确性的内容应删除、下沉或改为链接。

如果任务是精简或重写现有文档，比较改写前后的主文长度与结构。除非用户要求补充缺失事实，否则主阅读路径变长视为未通过，应继续压缩。

压缩前先建立一份不写入正文的覆盖清单：为每个读者问题列出不可丢失的调用边界、状态语义、安全边界、限制条件和可信门槛，并为源材料中的每条有效事实标记去向：正文、附录或资料索引、用户明确授权删除。删掉解释性展开，而不是删掉清单中的契约；交付前逐项确认这些事实恰好出现一次。保持源材料的证据强度和语气：`可能`、`待核`、`不足以证明` 不得改写成 `阻塞`、`禁止` 或任何未经支持的正向结论。

### 附录保真

精简或重写现有文档时，默认保留源材料中的有效事实。未进入主阅读路径的信息必须满足以下之一：

- 进入附录，按内容自然分组，例如接口与字段、运行与安全、兼容与扩展、证据与待核项；
- 已有稳定、可访问且版本明确的事实源时，进入资料索引并链接到精确位置。

只有用户明确允许删除时才可直接省略。附录不计入主阅读时间预算，也不得与正文重复展开。

保持专业表达。除非用户明确要求教学材料，不添加入门教程、术语科普或为了显得完整而扩写的背景。

## 成品验收

交付前从读者视角检查最终承载页面，而不只检查源文本或独立图表：

1. 读者能否在预期时间内找到 1–3 个核心问题的答案？
2. 首屏是否已经说明文档解决什么问题以及核心结论？
3. 图中文字、方向和层级在普通阅读视口是否清晰？
4. 正文是否重复图表，或包含不服务读者任务的细节？
5. 事实、边界、失败状态和可信条件是否准确，没有为了简洁而损失关键约束？
6. 对精简任务，主阅读路径是否确实比原文更短，而不只是多了一层摘要？
7. 图表中的每条箭头、每个表格单元格、状态和包含关系是否能在源材料中找到依据，方向、列语义与调用关系是否正确？
8. 源材料中的每条有效事实是否都有明确去向；附录或资料索引是否可追溯且不与正文重复？

发现问题就继续重排、删减或重画，直到通过。不要把“已经写完”“材料齐全”或“工具调用成功”当作验收完成。

## 边界

- 用户当前请求优先于本流程；需要完整规范、审计底稿或教学材料时，不强行压缩为摘要。
- 文档任务不自动授权修改产品代码、原始资料或用户未指定的共享文档。
- 不套固定章节名称、固定图表数量或固定篇幅；结构服从读者任务。
